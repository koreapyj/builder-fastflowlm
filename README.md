# builder-fastflowlm

[FastFlowLM](https://github.com/ROCm/FastFlowLM) with Qwen3-TTS text-to-speech on the AMD NPU, kept as patches on top of upstream. This repository holds only the patches, the CI that builds FastFlowLM with them exactly as upstream builds and distributes it, and a local development workflow.

Upstream ref: [`support/upstream.env`](support/upstream.env) (`FLM_REF`, currently `d8767c0a`, which is `v1.0.9-41`).

## Patches

Each patch is self-contained: it applies alone to a clean `FLM_REF`, in any order, and never touches a file another patch touches.

| patch | what |
|---|---|
| [`0001-qwen3-tts-npu.patch`](patches/0001-qwen3-tts-npu.patch) | Qwen3-TTS engine (NPU talker and code predictor through the prebuilt `qwen3_npu` engine, CPU speech decoder), `/v1/audio/speech` and the streaming-text WebSocket, `flm run`/`flm serve` support, the `qwen3-tts:1.7b` model entry, unit tests. Linux + XRT only; compiled out on Windows and HRX builds. |
| [`0002-qwen3-tts-package-tools.patch`](patches/0002-qwen3-tts-package-tools.patch) | `src/tools/qwen3_tts/`: builds the model package from the Hugging Face checkpoint, calibrates the garble detector, test client, and the user README (build, run, API, limitations). |

FastFlowLM is distributed as upstream does: packages and portable tarballs contain no models. The Qwen3-TTS model package is built by the user with the tools in patch 0002 (`src/tools/qwen3_tts/README.md` once applied).

## CI

[`.github/workflows/ubuntu-build.yml`](.github/workflows/ubuntu-build.yml) and [`debian-portable.yml`](.github/workflows/debian-portable.yml) are upstream's own build workflows at `FLM_REF`, generated by [`support/sync-workflows.py`](support/sync-workflows.py) with three changes:

- each checkout becomes: this repository into `.builder/`, then [`support/prepare-source.sh`](support/prepare-source.sh) puts upstream at `FLM_REF` (with submodules) in the workspace root, checks the pinned engine binaries, and applies `patches/`; upstream's build steps then run unchanged, in upstream's build containers
- triggers: every branch, pull requests
- versions: upstream's `git describe` plus this repository's commit, e.g. `1.0.9-41-gd8767c0a+g1234abc` (`FLM_DESCRIBE` in `support/upstream.env`; `prepare-source.sh` fails if it no longer matches `FLM_REF`)
- releases: every push to the default branch publishes a release with upstream's release assets, tagged with upstream's version plus this repository's commit: `v1.0.9-41-gd8767c0a+g<commit>`. This repository has no tags of its own

So the outputs are upstream's: `.deb` packages for Ubuntu 24.04, 25.10, 26.04 and Debian 13, and the Linux portable tarballs (XRT, HRX, models-from-source), released as above. Upstream's Windows workflows run on upstream's self-hosted runners and are not mirrored (the Qwen3-TTS code is compiled out on Windows anyway).

[`qwen3-tts-checks.yml`](.github/workflows/qwen3-tts-checks.yml) adds this repository's own checks: every patch applies alone to a clean `FLM_REF`, and the text segmentation unit tests.

### Pinned engine binaries

The Qwen3-TTS fast path drives upstream's prebuilt `qwen3_npu` engine through interposed XRT calls and depends on its internals. [`support/pinned-binaries.sha256`](support/pinned-binaries.sha256) lists the engine libraries and xclbins it was validated against on the NPU; `prepare-source.sh` fails if `FLM_REF` has different ones.

## Local development

Requirements: `git`, `make`, `podman` or `docker` (builds run in upstream's CI image, `ghcr.io/rocm/fastflowlm/build-environment`, plus Rust, baked once into a local image).

```sh
make prepare        # upstream at FLM_REF into ./src, binaries checked, patches applied
make build          # incremental build -> src/src/build/flm   (DISTRO=ubuntu26.04 by default)
make test           # text segmentation unit tests
make deb            # dpkg-buildpackage as CI -> ./fastflowlm_*.deb
```

`./src` is an ordinary upstream checkout (ignored by this repository). Edit it, commit there or not, then:

```sh
make update         # regenerate patches/ from ./src: git diff FLM_REF, split by path
make check          # each patch applies alone to a clean FLM_REF
```

`make update` keeps each patch's description. A change belongs to `0002` if it is under `src/tools/qwen3_tts/`, otherwise to `0001`; a new independent change gets its own patch and its own line in [`support/update-patches.sh`](support/update-patches.sh).

### Updating FLM_REF

1. Set `FLM_REF` and `FLM_DESCRIBE` (its `git describe --tags --always`) in `support/upstream.env` (a tag or a commit), `make prepare` (in a fresh `./src`, or one without local changes) and fix any patch that no longer applies; `make update`, `make check`.
2. If `prepare` reports different engine binaries: the integration has to be revalidated on the NPU before the new ref can be used (the fast path harvests the engine's instruction streams and buffer layout); then update `support/pinned-binaries.sha256`.
3. `make sync-workflows` regenerates the CI from upstream's workflows at the new ref (`prepare` warns when they changed).
